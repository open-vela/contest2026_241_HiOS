## 0. 一句话结论

HiOS 是在 Cursor Agent 辅助下，把 Metalio Claw4（ESP-IDF）的功能与 UI，逐步移植到 openvela/NuttX 上的嵌入式 AIOS。开发主线是：**显示/触控打通 → 桌面与 App 对齐 → 小智聊天与唤醒 → 本地语音后端 → 蓝屏稳定化 → 传感器/电台对齐 → 赛事材料与工程文档**。

## 2. 开发时间线（按阶段）

### 阶段 A · 立项与显示触控（2026-08）

**对话主题：** HiOS MVP、视觉移植、屏幕/触控对齐 MetalioClaw4  

**典型需求：**
- 定默认方案（MVP 落地计划）
- 浏览器预览软主页（`preview` + `http.server`）
- 编译烧写到真机
- 修全黄 / 全黑 / 无背光
- 移植屏幕、显示、触控（对照 Claw4）

**过程要点：**
1. 先做 HTML 软主页验证交互与视觉，再落到板端 LVGL。
2. 踩过 NuttX framebuffer / GDMA 相关坑（频繁 pause/resume GDMA 会导致再次全黑等）。
3. 驱动侧按 metalio defconfig + Claw4 显示路径对齐，直到能出图、能点。

**阶段结果：** 板端能亮屏、有主页雏形；显示链路仍脆弱，后续大量「蓝屏」问题多与 LVGL/线程/刷新竞态相关。

### 阶段 B · 工程合并与固件形态（2026-09-03 ~ 09-04）

**对话主题：** 移植进度盘点、C5 移植、P4/C5 固件合并与烧录  

**典型需求：**
- 汇总移植到什么地步
- 按 `docs/porting/c5_nuttx_port.md` 继续 C5
- 不要只剩很小的固件；要把 P4 能力合进统一固件
- 参考 Claw4「一个 .bin」的烧录方式

**过程要点：**
1. 明确 HiOS 是双芯片方案，烧录与运行时分工需对齐 Claw4。
2. 早期合并烧录曾出现「只有黑背光、进不了引导/主页」，靠串口监听与回退路径排查。

**阶段结果：** 形成可重复的编译烧录流程；后续常用 `flash_espclaw.sh` / `esptool` + `/dev/ttyACM0`。

---

### 阶段 C · 小智聊天与「Hi 钛灵」唤醒（2026-09-04 ~ 09-08）

**对话主题：** 聊天 App 打通 xiaozhi.me、6 位绑定码、麦克风与唤醒  

**典型需求：**
- 聊天 App 走与小智相同的 6 位数字码绑定
- 修 SD 卡 FAT 未挂载导致设置/OTA 落盘失败
- 连 WiFi 后触控失灵
- 进入聊天应展示验证码，而不是一直「正在连接」
- 说「Hi 钛灵」唤醒进对话
- 唤醒后卡在「连接中」黄色提示

**过程要点：**
1. 绑定码、MQTT/OTA 配置与存储路径强相关；SD 挂载失败会连带语音通道异常。
2. 唤醒链路：麦克风 → WakeNet/能量检测 → UI 状态机 → MQTT/音频通道，任一环断都会「有串口 hit、界面无反馈」。
3. 用户多次强调：**只改当前问题，其它已调好的不要动**（成为后续协作默认约束）。

**阶段结果：** 云端小智路径可绑定、可唤醒；音频与 UI 状态机仍需多轮打磨。

---

### 阶段 D · 电台、HA、本地语音后端（2026-09-05 ~ 09-11）

**对话主题：** 电台蓝屏、Home Assistant / MCP、xiaozhi-esp32-server 本地化  

**典型需求：**
- 评估并重做电台 App（保留可用数据，UI 接近现有深色频谱风格）
- 聊天语音可打开「电台」
- 电台播放/切台时蓝屏、无声、卡在 HLS/DNS
- 聊天后台改本地 `xiaozhi-esp32-server`
- 激活码、server timeout、唤醒后无语音、第二句卡在「聆听中」、聊天气泡丢失

**过程要点：**
1. 电台问题集中在：页面销毁/创建与网络解码线程并发、HLS 拉流与 LVGL 刷新互相踩。
2. 改后端地址看似「只改配置」，实际会牵动会话状态机、超时、TTS/STT 与 UI 气泡刷新，因此出现大量「只改聊天、别动别处」的迭代。
3. 并行讨论了聊天控制本机 App、以及经 WiFi 控智能家居（HA / MCP）的架构路径。

**阶段结果：** 本地 esp32-server 可跑通语音对话主路径；电台与待机蓝屏进入「稳定化」攻坚期。

---

### 阶段 E · 蓝屏稳定化与本地控制（2026-09-12 ~ 09-13）

**对话主题：** 待机翻页时钟蓝屏、首次唤醒失败、本地音量/背光/蓝牙/开 App  

**典型需求：**
- 待机界面蓝屏；第一次语音唤醒失败要彻底修
- 聊天里音量、背光、蓝牙、打开本地 App：**走本地实现，不走云端 MCP**
- 去掉易触发蓝屏的蓝色粒子动效
- 固件永久写入、重启可用
- 串口常开便于抓 log
- 聊天气泡方框乱码、天气/计算器异常后要恢复

**过程要点：**
1. 「蓝屏」多数不是单纯 UI 配色，而是唤醒/对话时 LVGL 仍在刷新，或传感器/动画定时器与主线程冲突。
2. 本地指令与云端 MCP 分流：系统控制留在板端，对话理解可仍走服务器。
3. 调试方式固化为：烧录 → `capture_acm0.py` / 串口抓 log → 最小范围修复 → 再烧验证。

**阶段结果：** 首次唤醒与待机稳定性明显改善；本地控制能力接入聊天。

### 阶段 F · 传感器 / 电台 / 磁场水平仪对齐（2026-09-13 ~ 09-16）

**对话主题：** 抄 MetalioClaw4 的磁场、水平仪、电台界面；用 openvela 实现  

**典型需求：**
- 水平仪界面与 Claw4 一致且不蓝屏
- 磁场打开蓝屏 / 无界面，按 Claw4 加回功能与 UI
- 多 App 进出蓝屏，追根因（硬移植 UI、未做 NuttX 适配）
- 电台重写评估与竹知了 App 完善

**过程要点：**
1. 部分 App「只搬了 UI，没做 NuttX 适配」是批量蓝屏的根因之一。
2. 水平仪校准、磁场打开路径反复真机验证；强调自动抓串口继续修。

**阶段结果：** 传感器类 App 向 Claw4 视觉与行为靠拢；稳定性仍需按 App 逐个收口。

## 3. 协作模式（从对话中沉淀的工作方式）

1. **先评估后动手**：电台重写、4G 适配、系统级唤醒等，用户常要求「先回答 / 先评估，先不操作」。
2. **最小改动**：反复出现「只改这个问题，其它都不要动」——避免回归。
3. **真机闭环**：改代码 → 编译 → 自动烧录 → 串口验证 → 根据现象再改。
4. **对照源优先**：功能与 UI 以 MetalioClaw4 为金标准，实现落在 openvela/NuttX。
5. **问题分类**：配置/后端切换、UI 线程安全、驱动/GDMA、存储挂载，四类问题不要混修。

## 4. 问题图谱（高频真机现象）

| 现象 | 常见原因方向 | 协作中的处理策略 |
|------|--------------|------------------|
| 全黑 / 无背光 | 供电、背光 GPIO、GDMA/显示初始化 | 对照 Claw4 驱动时序，避免错误 FB 路径 |
| 进入 App 即蓝屏 | LVGL 对象生命周期、页面切换竞态 | 缩小改动面；抓串口卡点（如 `APP_GO` / `JOB_RUN`） |
| 待机翻页时钟蓝屏 | 动画/粒子定时器与系统休眠/刷新冲突 | 去掉高风险动效；修根因后再加特效 |
| 唤醒有 hit、UI 无反应 | 状态机、MQTT、音频服务未就绪 | 对表串口 `WAKE hit` 与界面状态 |
| 第二句对话卡住 | 会话状态未复位、listening 死锁 | 只动聊天状态机与音频路径 |
| 改后端后一堆异常 | 超时、激活、气泡刷新耦合 | 承认「改地址」会影响会话链路，按聊天子系统收口 |
| SD/设置失败 | FAT 未挂载 | 先修挂载，再谈 OTA/绑定持久化 |

## 7. 工程速查

```bash
# 典型编译（在仓库根或 nuttx 目录，以当前脚本为准）
./build.sh nuttx/boards/risc-v/esp32p4/metalio-claw-4/configs/nsh -j$(nproc)

# 烧录示例
cd nuttx && ./flash_espclaw.sh /dev/ttyACM0
# 或
esptool.py -c esp32p4 -p /dev/ttyACM0 -b115200 write_flash 0x2000 nuttx.bin

# 串口抓启动/运行日志（示例）
python3 capture_acm0.py
```

关键路径见仓库根 `README.md`。

## 8. 后续建议（从协作中自然长出）

1. **按 App 做 NuttX 适配清单**：对仍「硬搬 UI」的页面，逐个补生命周期与线程边界，减少进出蓝屏。
2. **唤醒词若要「真换」**：除文案外，需替换 WakeNet 模型与 `srmodels` 注释，不能只改字符串。
3. **对话记录落盘**：若要导出板端人机对话内容，需在 `SetChatMessage` 等路径写 SD/日志；串口目前多半只有类型与状态。
4. **本地控制与 HA**：保持「板端能力本地执行、家居能力走 HA」的清晰边界，避免开灯类指令冲突。
